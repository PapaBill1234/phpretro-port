# G02/G04/G09: account and housekeeping slice

This slice adds password login for existing Polaris users and durable CMS settings updates. It does not issue game SSO, create game users or claim emulator handshake compatibility. Polaris remains the identity/password authority; `username` and `account_created` integer seconds are read through a separate, read-only bridge connection. CMS roles are explicit CMS records, never derived from Polaris rank. Account, IP and matching known-machine bans deny login and existing-session use.

Authentication uses bcrypt verification, 256-bit opaque session cookies, Redis TTL sessions and per-IP/account login limits. Password/token-version changes revoke sessions on the next request through live identity checks. Redis failure denies authentication and mutations. Session token keys are hashed; passwords, cookies, MFA codes and CSRF values never enter logs. Session duration is fixed (8 hours), without a silent sliding lifetime.

`CMS_PUBLIC_ORIGIN` is a single configured origin. State-changing requests require that exact Origin; authenticated writes also require an in-memory CSRF token obtained from same-origin session JSON. Production cookies are Secure, HttpOnly, SameSite=Lax, host-only, Path=/; insecure cookies require an explicit loopback HTTP origin. Forwarded IP headers are ignored unless the direct peer matches explicit trusted proxy CIDRs. JSON input has a size limit, exact supported fields and rejects unknown/trailing data.

CMS staff require TOTP at login. Secrets are AES-GCM encrypted at rest using a separate 32-byte environment key. TOTP accepts only six digits in a bounded +/- one-step window and rejects replay through a durable, conditional update of only the last accepted TOTP step in MariaDB (Redis restart must not reset replay protection). Live role revisions and separate random MFA enrollment revisions invalidate the whole prior staff session, including delete/re-enroll with the same role. Redis deletion is confirmed before returning guest status; deletion failures deny access. AES-GCM envelope is version byte1, 12-byte nonce and sealed20-byte secret with16-byte tag. AAD is ASCII `phpretro-staff-mfa:v1:user:<positive-decimal-user-id>:credential:<64-lowercase-hex-enrollment-revision>`. Relocating a ciphertext to another user/enrollment must fail. Enrollment is an operator CLI using the migration principal, verifies the game identity and writes the enrollment secret only to a new mode-0600 file; no HTTP role assignment or default staff account. No social OAuth or reset-mail flow is simulated.

## HTTP ABI

- `POST /api/v1/auth/login`: `{username,password,otp?}`. Returns `session.v1` with `authenticated:true`, `user:{id,username,role}` (`member` or `admin`), `csrfToken`. Sets an opaque cookie. Invalid credentials/bans/MFA return the same generic 401. Rate limit=429, unavailable dependency=503. Cookie replacement revokes the previous session.
- `GET /api/v1/auth/session`: same ABI; guests get `{version:"session.v1",authenticated:false}`. Invalid/revoked cookies are cleared. No-store; no CORS credentials.
- `POST /api/v1/auth/logout`: requires exact Origin and `X-CSRF-Token`; deletes the session, clears cookie, returns guest session. Fails closed if deletion cannot be confirmed.
- `GET /api/v1/housekeeping/site`: live admin+MFA required. Returns existing `site.v1`.
- `PUT /api/v1/housekeeping/site`: same admin checks, Origin and CSRF. Input `{version:"site-update.v1",siteName,activeTheme,defaultLocale,enabledLocales,expectedRevision}`. Allows only `legacy|modern`, `en|nl`, nonempty unique locales including default. Returns updated `site.v1`. Revision conflict=409. The mutation locks the authoritative staff record first, revalidates session role and MFA revisions, then locks/updates settings and inserts audit in one transaction; operator grant/revoke follows the same staff-row-first order. Settings and audit event commit in one transaction; runtime has UPDATE only for settings and the last-TOTP-step column, and INSERT only for audit. Public site reads live DB settings, so no stale cache may authorize a mutation.

React consumes this ABI via a typed controller and original account/housekeeping panel, in both en/nl and both original theme shells. Tokens remain in component memory; no localStorage/sessionStorage, fake logged-in principal or fake success. Errors remain visible. Preview settings are separate from persisted housekeeping settings.

## Acceptance

Negative fixtures: missing Origin/CSRF; malformed/oversized JSON; invalid/duplicate identity; bans; stale password/version; expired/replayed TOTP; removed/changed staff role; unauthenticated/member mutation; Redis outage; concurrent revision conflict and audit rollback. Disposable MariaDB+Redis tests prove epoch scans, read-only adapter grants, migrations preserving settings and real persistence. Browser smoke remains an acceptance requirement; the current environment has no enabled browser surface, so source/controller tests and HTTP fixtures do not establish browser interaction. Independent Sol reviews architecture before implementation and final source/diff before publication.

Architecture checkpoint: native Sol reviewed the design and source on2026-10-11. Its separate MFA-revision and in-transaction authorization findings are incorporated above. Login retains the exact password-hash/token-version snapshot that was verified; it never upgrades to a newly read credential version after a concurrent reset. Ordered additive migration checksums and least-privilege grants require integration fixtures. The native CLI reported36 turns despite20 configured; only its external wall-time bound is verified, and no turn/cost cap is claimed.
